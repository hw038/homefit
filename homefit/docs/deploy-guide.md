> 대상: 이 저장소를 받아 **자기 AWS 계정(또는 다른 환경)에서 직접 수집·저장·서빙**하려는 개발자.
> 기준일 2026-11-17. 외부 API 세부(파라미터·한도·요금)와 법·제도 내용은 작성자 지식 기준이며 **[확인 필요]** 로 표시한 곳은 반드시 원문을 확인하세요.

## 0. 한눈에 보기

### 지금(캡스톤 MVP) 구조
```
[Claude 세션] ──MCP search_trades──▶ 서울 열린데이터광장 API
      │  (결과가 크면 세션 파일로 저장, 작으면 에이전트가 옮겨 적음)
      ▼
 tools/ingest.py ─▶ data/trades/*.json (로컬 파일)
                          │  서버 시작 때 전부 읽어 메모리에서 집계(약 1~2초)
 mydata/pseudo/*.csv ─────┤
 (합성 가명 고객)          ▼
                 server.py (파이썬 표준 http.server, 프로세스 1개)
                    │  127.0.0.1 / 0.0.0.0:8765
   Valkey(로컬) ◀───┤  좋아요·급상승, pub/sub → SSE
                    ▼
        CloudFront(비밀 헤더) ─▶ 인터넷
```

### 권장 운영 구조
```
EventBridge Scheduler (매일 새벽)
   └▶ Step Functions ─(25개 구 병렬)─▶ 수집 Lambda/Fargate ──▶ 서울 열린데이터광장 · 국토부 API
                                         │ 원본 그대로
                                         ▼
                          S3 raw/ (비공개·암호화·버전 관리)
                                         │ 정제·비식별(지번 삭제, 단지 해시 HMAC)
                                         ▼
                          S3 curated/ (Parquet 또는 JSON)
                                         │ 집계 작업(market.build) + 품질 게이트
                                         ▼
                          S3 serving/ (셀·단지·월별 추이 JSON, 버전 태그)
                                         │ 시작 때 또는 주기적으로 로드
CloudFront + WAF ─▶ ALB ─▶ ECS Fargate (API·화면, 2개 이상) ◀─▶ ElastiCache for Valkey (좋아요·pub/sub)
                                 │
                                 ├─ Secrets Manager (API 키, HMAC 키, 원본 확인 헤더)
                                 ├─ RDS/Aurora (실고객 데이터를 받는 경우에만, 서울 리전)
                                 └─ CloudWatch (로그·지표·경보)
```

## 1. 지금 MVP가 샌드박스에 기대고 있는 것 (외부에서 그대로는 안 되는 이유)

| # | 지금 방식 | 외부에서 생기는 문제 | 바꿀 방향 (절) |
|---|---|---|---|
| 1 | 실거래를 **Claude 세션의 MCP 도구**로 수집. 결과가 크면 세션 파일, 작으면 에이전트가 손으로 옮겨 적고 독립 사본으로 대조 | 사람·에이전트가 있어야 수집됨. 반복·자동화 불가. 옮겨 적기 오류 위험 | 직접 API를 부르는 배치 수집기 (§2.1, §4.1) |
| 2 | MCP 도구가 **신고 연도(RCPT_YR) 기준 최근 5,000건**만 훑고, 1회 1,000건 상한 | 거래 많은 구의 연초 달이 0건으로 옴(송파·강서·노원 등 2026.1~3월). 12월 계약을 1월에 신고한 건 누락 | 페이지 끝까지 순회, 신고 연도 2개 조회, 또는 국토부 API(계약월 기준) (§2.1) |
| 3 | 고객 데이터 = **합성 가명 CSV** (`mydata/pseudo`) | 실제 서비스에는 쓸 수 없음. 실제 마이데이터는 허가 없이 받을 수 없음 | 직접 입력·제휴·합성 데이터 중 선택 (§2.2) |
| 4 | 서버가 **시작할 때 모든 거래를 읽어 집계** (15만 행 ≈ 1~2초, 메모리) | 데이터가 늘수록 시작이 느려지고, 데이터 교체마다 재시작 필요 | 집계를 배치로 미리 만들어 두고 서버는 결과만 로드 (§3.3, §4.2) |
| 5 | 파이썬 **표준 http.server** 1개 프로세스 | 동시 접속·SSE 연결이 늘면 스레드 고갈. 무중단 배포 불가 | ASGI(예: Starlette/FastAPI + uvicorn) 컨테이너 2개 이상 (§4.2) |
| 6 | Valkey가 **같은 서버의 로컬 프로세스** | 서버가 여러 대면 좋아요·실시간 알림이 갈라짐. 백업 없음 | 관리형 Valkey(ElastiCache) 하나를 모든 인스턴스가 공유 (§3.4, §4.3) |
| 7 | 요청 수 제한을 **앱 메모리**에서 IP별로 셈 | 인스턴스마다 따로 세므로 여러 대면 제한이 느슨해짐 | CloudFront + AWS WAF 속도 기반 규칙 (§5.2) |
| 8 | 비밀 값이 **파일**(`data/.origin_secret`), API 키는 MCP 등록에만 | 서버 이전·교체 때 유출·분실 위험, 교체(rotation) 절차 없음 | Secrets Manager (§5.1) |
| 9 | 단지 해시(cid)가 **솔트 없는 SHA-256** | 공개 주소 목록으로 역산 가능 | 비밀 키로 HMAC (§3.2) |
| 10 | 규제 수치가 **수작업 `policy.json`**, 지식 기준 2026-06 | 정책이 바뀌면 계산이 틀림 | 시행일 포함 버전 관리 + 정기 점검 (§2.3) |
| 11 | 배포가 **수작업**(백그라운드 프로세스, systemd 미등록) | 재부팅·세션 종료 시 서비스 중단 | 컨테이너 + IaC + CI/CD (§6.1) |
| 12 | 모니터링 없음 | 수집 실패·데이터 노후화를 모름 | CloudWatch 지표·경보, 데이터 신선도 점검 (§6.2) |
| 13 | 실행 리전 us-east-1 | 실고객 개인정보를 다루면 국외 이전 문제 | 고객 데이터는 서울 리전(ap-northeast-2) (§5.3) |

## 2. 데이터별 수집 방법

### 2.1 실거래 (부동산 매매 신고)

#### 출처 선택
| 출처 | 장점 | 주의 |
|---|---|---|
| **서울 열린데이터광장** `tbLnOpendataRtmsV` (지금 사용) | 서울 전체·여러 용도(아파트·연립·오피스텔·단독)를 한 API로. 해제일(RTRCN_DAY), 신고구분(중개/직거래) 포함 | 평문 HTTP(포트 8088), 키가 URL 경로에 들어감. 1회 최대 1,000건. 조회 조건이 신고 연도(RCPT_YR)·자치구 중심이라 계약월로 바로 못 거름 |
| **국토교통부 실거래가 공개 API** (공공데이터포털, 아파트 매매 실거래 상세) [확인 필요] | 법정동 5자리 코드(LAWD_CD)와 **계약 연월(DEAL_YMD)** 로 조회 → 계약월 누락 문제가 없음. 전국 | 서비스키 발급·일일 호출 한도 있음 [확인 필요]. 용도별로 API가 나뉨. 응답 형식(XML/JSON)과 필드명이 다름 |

권장: **국토부 API를 기본, 서울 열린데이터광장을 보조·대조용**으로. 두 출처를 같은 스키마로 맞추는 어댑터를 둡니다.

#### 서울 열린데이터광장으로 계속 쓸 때 꼭 고칠 점
1. **페이지를 끝까지 순회**: `START_INDEX`/`END_INDEX` 로 1,000건씩, 응답의 전체 건수(`list_total_count`)까지 반복. 지금 MCP 도구의 "최대 5페이지" 제한을 없앱니다.
2. **신고 연도를 두 해 조회**: 계약 월 M의 거래는 M월~M+1월에 신고되므로, 12월 계약은 이듬해 신고분에도 있습니다. 대상 계약월이 속한 해와 그다음 해의 신고분을 모두 받아 **계약일(CTRT_DAY)로 거릅니다**.
3. **HTTPS 가능 여부 확인** [확인 필요]: 지원되면 HTTPS로, 아니면 키 노출 위험을 문서화하고 키를 자주 교체.
4. **자치구 코드(CGG_CD)로 조회**: 이름(CGG_NM) 표기 차이를 피합니다.

#### 수집 주기와 증분 전략
- 신고 기한이 **계약 후 30일**이고 해제(취소)는 그 뒤에도 들어오므로, **매일 최근 3개월을 다시 받아 덮어쓰기(upsert)** 하고, 그보다 오래된 달은 **주 1회** 다시 받아 해제 반영을 확인합니다.
- **멱등 키**: (자치구, 법정동, 지번, 건물명, 계약일, 금액, 전용면적, 층, 해제일). 원본에 **완전히 같은 행이 두 번 오는 경우가 실제로 있어서**(이번 수집에서 1,673건) 중복 제거가 필요합니다.
- 받은 원본은 **가공하지 말고 그대로** raw 계층에 저장(응답 원문 + 요청 파라미터 + 받은 시각). 가공은 다음 단계에서.

#### 품질 점검(수집 직후 자동)
| 점검 | 실패 시 |
|---|---|
| 구·월별 건수가 지난 수집 대비 급감(예: 50% 이상) | 발행 중단 + 경보 (조회 한도·API 장애 가능성) |
| 1,000건 정확히 = 페이지 끝까지 못 받음 | 재시도 |
| 필수 필드(금액·면적·계약일) 누락 비율 | 경보 |
| 계약일이 요청 월 밖 | 버림(지금 ingest.py와 같음) |
| 최근 달(신고 기한 중) | '잠정' 표시 유지 |

### 2.2 고객 재무 데이터 (마이데이터를 그대로 쓸 수 없는 문제)

지금 앱은 **합성 가명 데이터 1,000명**으로 동작합니다. 실제 서비스에서 고객의 계좌·카드·대출 정보를 금융회사에서 직접 받아 오는 것은 **마이데이터(본인신용정보관리업)** 에 해당하고, 금융위원회 허가와 엄격한 보안·동의 요건이 필요합니다 [확인 필요: 신용정보법 세부]. 허가 없이 스크래핑으로 대신하는 것은 피해야 합니다.

| 방식 | 방법 | 장점 | 부담 | 권장 용도 |
|---|---|---|---|---|
| **A. 사용자가 직접 입력** | 연소득, 예금·증권 합계, 대출 잔액·금리·유형, 보유 주택 수, 월 지출 | 허가 불필요, 바로 가능. 계산에 필요한 값만 받음 | 입력이 부정확할 수 있음 | **1차 출시 권장** |
| **B. 마이데이터 사업자와 제휴** | 허가 사업자가 고객 동의를 받아 표준 API로 받은 뒤, 계산에 필요한 **요약값만** 넘겨받기 | 정확, 고객 편의 | 계약·보안 심사·동의 설계, 제3자 제공 요건 [확인 필요] | 정식 서비스 단계 |
| **C. 직접 마이데이터 허가 취득** | 본인신용정보관리업 허가 | 완전한 통제 | 자본금·보안 인증·인력 요건 등 매우 큼 [확인 필요] | 사업 규모가 클 때만 |
| **D. 합성 데이터** | 지금 `mydata/pseudo` 구조로 생성기를 만들어 데모·테스트에 사용 | 개인정보 없음, 공개 데모 가능 | 현실성 낮음(이번에도 자산 규모가 작아 기본 조건 후보 0곳) | 데모·개발·테스트 |

**설계 원칙 (어느 방식이든)**
- **최소 수집**: 계산에 필요한 건 자기자본, 연소득, 기존 대출의 연 원리금, 보유 주택 수, 월 지출 정도입니다. 거래 내역 원본은 받지 않거나 받아도 즉시 요약 후 폐기합니다.
- `budget.py` 의 `build_profile()` 이 하는 일이 "원장 → 요약값" 변환입니다. 외부에서는 이 단계를 **입력 경로별 어댑터**로 바꾸고, 계산부(`compute_budget()`)는 요약값만 받게 유지합니다.
- 실고객 데이터는 **공개 경로에 절대 두지 않습니다**. 로그인(예: Amazon Cognito) 뒤, 본인 데이터만 조회.

### 2.3 대출·세금 규칙 (정책 데이터)
- `policy.json` 을 **시행일(valid_from) 단위 버전**으로 관리합니다. 예: `policies/2025-10-16.json`. 계산할 때 기준일에 맞는 판을 고릅니다.
- 출처: 금융위원회·국토교통부 보도자료, 은행연합회·은행 공지. 원문 링크와 확인 날짜를 함께 저장합니다.
- **정기 점검**: 분기 1회 + 대책 발표 시. 특히 서울 토지거래허가구역은 **2026-12-31 만료 예정**이라 연장 여부를 바로 반영해야 합니다.
- 화면의 `data/policy_history.json` (정책 히스토리)도 같은 저장소에서 관리합니다.

### 2.4 좋아요·열람 (행동 데이터)
- 익명 브라우저 ID 기준. 고객 데이터와 연결하지 않습니다.
- 보존 기간을 정합니다(예: 시간별 집계는 30시간 뒤 자동 삭제 — 지금 구현). 누적 좋아요는 남기되, 오래된 익명 ID 집합은 주기적으로 정리.
- 남용 방지는 앱보다 **WAF 속도 제한 + 로그인 사용자만 좋아요** 쪽이 확실합니다.

## 3. 저장·관리 (데이터 계층)

### 3.1 S3 데이터 레이크 계층
| 계층 | 내용 | 접근 | 형식 |
|---|---|---|---|
| `raw/source=seoul|molit/gu=…/ym=…/fetched=…/` | API 응답 원문 + 요청 정보 | 수집 작업만 쓰기, 사람 읽기 제한. **지번 포함이라 비공개** | 원문(JSON/XML) |
| `curated/trades/ym=…/` | 정제·중복 제거·비식별(지번 삭제, 단지 해시 HMAC, 단지명은 정책에 따라) | 집계 작업 | Parquet 권장(지금은 JSON) |
| `serving/v=YYYYMMDDHHMM/` | 셀·단지·월별 추이·구 요약·제외 내역 (지금 `market.build()` 결과) | 웹 서버 읽기 | JSON(작음), `latest` 포인터 |
| `meta/` | 수집 매니페스트(파일별 행 수·sha256), 검증 기록, 정책 판 | 운영 | JSON |

- 버킷: **버전 관리, 공개 차단, 기본 암호화(SSE-KMS 권장)**, 수명 주기(raw 1년 뒤 Glacier 등).
- 지금 만들어 둔 백업 스크립트(`tools/s3_backup.sh`)는 이 구조의 `curated/`·`meta/` 에 해당합니다.
- 질의가 필요하면 Glue 데이터 카탈로그 + Athena로 curated 계층을 SQL로 봅니다.

### 3.2 비식별과 단지 식별자
- 지번(본번·부번)은 curated 단계에서 버립니다(raw에만 남김).
- 단지 해시는 **HMAC-SHA256(비밀 키, 구|법정동|본번|부번|건물명)** 로 바꿉니다. 비밀 키는 Secrets Manager. 지금처럼 솔트 없는 해시는 공개 주소 목록으로 되돌릴 수 있습니다.
- 단지명은 이번 프로젝트에서 "아파트 추천 화면에서만" 쓰기로 했습니다. 외부 운영에서도 **공개 API 응답에 원시 거래 행을 내보내지 않는** 원칙을 유지합니다(지금 앱은 동네·단지 집계만 내보냄).
- 건물명 칸에 지번이 들어 있는 경우가 있어 `market.clean_name()` 처럼 지번 형태를 지웁니다.

### 3.3 서빙용 데이터
- 지금 서버는 시작할 때 모든 거래를 읽어 집계합니다. 외부에서는 **집계를 배치 작업으로 옮기고**, 서버는 `serving/latest` 만 읽어 메모리에 올립니다(수 MB).
- 새 판이 나오면 서버가 주기적으로(예: 10분) `latest` 를 확인해 **재시작 없이 교체**(원자적 참조 교체).
- 이렇게 하면 서버 시작이 빨라지고, 데이터 갱신과 코드 배포가 분리됩니다.

### 3.4 좋아요 저장소
| 선택지 | 특징 |
|---|---|
| **ElastiCache for Valkey** (권장) | 지금 코드(`likes.py`, RESP)를 그대로 사용. pub/sub로 여러 서버에 실시간 알림. 서버리스 옵션 있음 [확인 필요: 요금] |

## 4. 컴퓨팅 구성

### 4.1 수집·집계 배치
```
EventBridge Scheduler (매일 03:00 KST)
  └─ Step Functions
       ├─ Map(25개 구, 동시 5~10) ─ 수집 작업: 최근 3개월 + (주 1회) 과거 재확인
       │     재시도: 지수 백오프 3회, API 오류 코드별 분기
       ├─ 정제·비식별 작업 (curated)
       ├─ 품질 게이트 (§2.1 점검표) ── 실패 → 발행 중단 + SNS 경보
       └─ 집계 작업 (market.build → serving/v=…) → latest 포인터 갱신
```
| 작업 | 실행 환경 | 이유 |
|---|---|---|
| 구별 수집 | **Lambda** (15분 한도 안, 구·월 단위로 쪼갬) 또는 Fargate 작업 | 짧고 병렬. 호출 수 적어 비용 미미 |
| 집계(market.build) | **Fargate 작업**(1 vCPU·2 GB 정도) | 전체 데이터를 한 번에 메모리로 처리. 지금 15만 행 기준 수 초 |
| 백필(과거 몇 년) | Fargate 1회성 | 시간이 길 수 있음 |

- API 키는 Secrets Manager에서 읽고, **로그·예외 메시지에 URL(=키) 을 남기지 않습니다**(지금 `seoul-realestate/server.py` 의 처리 방식을 유지).
- 외부 호출 대상은 NAT 게이트웨이 + **아웃바운드 허용 목록**(네트워크 방화벽 또는 프록시)으로 제한합니다. 지금 net-guard 훅이 하던 역할을 네트워크 계층에서 합니다.

### 4.2 웹·API 서버
- **컨테이너화**: `Dockerfile` (python:3.12-slim 이상, 비루트 사용자, 읽기 전용 파일 시스템).
- **서버 교체**: 표준 `http.server` 는 데모용입니다. 핸들러 로직(`App` 클래스 메서드)은 그대로 두고, ASGI 프레임워크(예: Starlette/FastAPI)로 라우팅만 옮기면 됩니다. SSE는 비동기로 처리해 연결당 스레드를 쓰지 않게 합니다.
- **실행**: ECS Fargate 서비스 2개 작업 이상(가용 영역 분산), ALB 뒤. 대안: App Runner(더 단순, SSE·타임아웃 제약 확인 필요).
- **크기**: 서빙 데이터가 수 MB라 0.5 vCPU·1 GB로 시작. CPU 기준 자동 확장.
- **타임아웃**: SSE는 ALB 유휴 시간 제한(기본 60초)보다 짧은 주기로 신호를 보냅니다(지금 15초). CloudFront 원본 응답 시간 제한도 60초 이상.

### 4.3 실시간(SSE)과 여러 서버
- 지금 구조(서버마다 Valkey 구독 스레드 하나 → 접속자 대기열)는 **서버가 여러 대여도 그대로 동작**합니다. 모두 같은 Valkey 채널을 구독하기 때문입니다.
- 연결 수가 많아지면(수천 이상) SSE 전용 서비스로 분리하거나 API Gateway WebSocket을 검토합니다.

### 4.4 비용 감(월, 작은 규모) [확인 필요: 최신 요금]
| 항목 | 규모 | 대략 |
|---|---|---|
| Fargate 웹 2작업(0.5 vCPU·1 GB) | 상시 | 수십 달러 |
| ALB | 1개 | 20달러 안팎 |
| ElastiCache Valkey | 최소 노드 또는 서버리스 | 수~수십 달러 |
| Lambda·Step Functions·EventBridge | 하루 1회 | 1달러 미만 |
| S3·CloudFront·WAF | 데모 트래픽 | 수~십수 달러 |
| NAT 게이트웨이 | 1개 | 30달러 이상(데이터 처리 별도) — 비용이 크면 수집 작업만 퍼블릭 서브넷/VPC 엔드포인트 조합 검토 |

## 5. 보안·개인정보

### 5.1 비밀 관리
| 비밀 | 지금 | 외부 |
|---|---|---|
| 서울/국토부 API 키 | MCP 등록 환경 변수 | Secrets Manager, 수집 작업 역할만 읽기, 분기 교체 |
| 원본 확인 헤더 값 | `data/.origin_secret` 파일 | Secrets Manager + CloudFront 사용자 정의 헤더, 교체 시 두 값 동시 허용 기간 |
| 단지 해시 HMAC 키 | 없음(솔트 없는 해시) | Secrets Manager, 바꾸면 전체 재처리 |
| Valkey 인증 | 없음(로컬 전용) | ElastiCache 인증(AUTH/IAM) + TLS |

### 5.2 공개 경로 보호
- **CloudFront + AWS WAF**: 속도 기반 규칙(IP당 분당 요청), 관리형 규칙(봇·알려진 악성 IP), 필요하면 국가 제한.
- 원본 보호: 지금은 "보안 그룹(CloudFront 대역) + 비밀 헤더". 외부에서는 **CloudFront VPC 원본**(ALB를 인터넷에 열지 않음)을 권장합니다 [확인 필요: 지원 리전·구성].
- 앱 안의 요청 제한(`RateLimit`)은 서버가 여러 대면 정확하지 않으니 WAF가 1차, 앱은 2차 방어로 둡니다.
- 지금 앱은 `CloudFront-Viewer-Address` 만 신뢰합니다(위조 가능한 `X-Forwarded-For` 왼쪽 값을 쓰지 않음). 구성을 바꿀 때도 유지하세요.

### 5.3 개인정보·규제
- **실거래 데이터**: 공개 데이터지만 지번+건물명+층+계약일 조합은 특정 세대를 가리킬 수 있습니다. 공개 화면에는 집계만, 원시 행은 비공개.
- **고객 데이터**: 개인정보보호법·신용정보법의 동의, 목적 외 이용 금지, 가명정보 처리 기준을 따릅니다 [확인 필요]. 가명정보를 외부에 공개하는 일(이번 데모의 합성 데이터 공개 포함)은 실데이터에서는 하지 않습니다.
- **국외 이전**: 실고객 데이터는 서울 리전에 두고, 해외 리전(예: us-east-1) 처리는 피하거나 고지·동의 요건을 확인합니다 [확인 필요].
- **로그**: 요청 로그에 고객 번호·금액을 남기지 않습니다. 지금 서버는 경로만 남깁니다.
